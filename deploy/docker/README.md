# Docker

`docker-compose.yml` at the repository root starts Postgres, the API, the worker and the web app. Follow `docs/08-DEPLOY-HETZNER.md` (it uses this file). Ports are bound to 127.0.0.1, so put a reverse proxy (Caddy, see `deploy/hetzner/Caddyfile`) in front for HTTPS.

Status: the compose file passes `docker compose config` and YAML parsing. The GitHub CI workflow builds both images and starts the whole stack (database, API, worker, web) and checks that the API and the web app answer. No deploy to a real host was done. The `.env` must have `DEMO_MODE=false`, a real `SESSION_SECRET` (32 or more random characters), `OWNER_PASSWORD_HASH` and a `POSTGRES_PASSWORD` of letters and digits (`openssl rand -hex 24`), or the API will not start. The API reads the visitor address only from `FORWARDED_ALLOW_IPS` (compose sets the private network that holds the web container).

**Pinning the base images.** The Dockerfiles use the floating tags `python:3.12-slim` and `node:22-slim`, so a rebuild can pick up a newer image. To make a build repeatable, look up the digest of the tag you tested (`docker buildx imagetools inspect python:3.12-slim`, the line `Digest: sha256:...`), then write `FROM python:3.12-slim@sha256:<that digest>` in `apps/api/Dockerfile`, and the same for `node:22-slim` in `apps/web/Dockerfile` (two `FROM` lines). Update the digest on purpose when you want newer security fixes, and run the tests again.
